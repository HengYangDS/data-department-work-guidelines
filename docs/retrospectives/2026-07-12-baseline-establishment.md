# 准则基线建立与发布复盘

> **日期**：2026-07-12
>
> **状态**：基线已发布；部门采用效果待试运行验证
>
> **适用范围**：本项目的 `guidelines.md`、入口文件及其后续演化
>
> **正文权威**：[guidelines.md](../../guidelines.md)

## 1. 这次变更要解决什么

团队需要一套同时约束成员与 Agent 的通用工作质量契约，改善逻辑建模、分析解决问题、
口头沟通、行文表达以及人智协作的能力。此前这些要求散落在个人反馈、招聘材料、项目经验
和工具使用习惯中，难以形成共同语言，也无法稳定传递给 Agent。

本次只建立通用基线；不以一份泛化文档替代项目事实、岗位边界、业务语义或局部工程规则。

## 2. 决定与边界

- **`guidelines.md` 是唯一正文事实源**：避免 README、提示词、项目规则各写一套
  通用原则。局部项目只能引用并补充本地事实与验收，不能复制后分叉。
- **以《问道》作为判断约束**：让原则从真实、边界、尺度、责任和演化推导，而不是从
  管理口号堆砌。根文不映射为功能、模块或玄学命名。
- **使用“原则—可信内核—工作闭环—场景规则”结构**：先回答为什么，再说明怎样做，最后
  提供可操作模板。低风险任务不强制完整表单。
- **人是责任主体，Agent 是能力杠杆**：Agent 能扩展检索、推理和执行，但无法承受组织
  授权与后果。高风险动作仍需有权的人确认与验收。
- **规则必须有生命周期**：防止准则自身成为复杂度来源。新规则要有失败模式、净增益、
  验证和废止条件。

## 3. 已形成的能力

1. **共同认知语言**：区分事实、假设、推断、判断、决策和行动；区分行动权威与事实权威。
2. **可信交付机制**：以“权威 → 对象 → 承诺 → 变更 → 证据 → 主张 → 记录”约束完成声明。
3. **数据部门质量底线**：要求数据来源、可观测时间、语义、变化、质量与使用边界可解释。
4. **人智协作边界**：提供委托契约、停止升级条件、并行规则、完成报告与人工验收清单。
5. **组织演化入口**：定义真实样本校准、质量信号、规则试验、复审和废止机制。

## 5. 得到的经验

### 5.1 原则必须生成规则，而不是装饰规则

如果原则仅是开场语，后续条款就会重新变成并列的管理要求。将根本原则显式推导为权威、边界、证据、责任、简约和演化规则，才能让成员在新情境中自行判断，而不只是记忆清单。

### 5.2 根文应约束判断，不应吞没工程语义

《问道》提供的是对真实、微弱信号、自然形态、尺度与演化的约束。把它逐行映射为流程模块或为工程对象另造玄奥名称，只会增加解释负担并弱化事实边界。工程名称保持朴素，判断保持可证。

### 5.3 通用准则与项目规则必须分层

通用准则负责认知与协作底线；项目规则负责权威事实源、局部权限、运行方式和验收命令。把两者混在一起会使通用文件失去稳定性，也会使局部事实被错误泛化。

### 5.4 Agent 治理的核心不是提示词，而是责任链

高质量委托需要目标、事实源、范围、权限、验收、停止条件和交接，而非更长的自然语言指令。成员是否核验并承担结果，决定了 Agent 是能力杠杆还是风险放大器。

### 5.5 先试运行，再增加制度

本版本已较完整；下一步不应继续扩写。应在分析研究、生产诊断和人智协作三类真实工作中试用，依据返工、质量逃逸、交接质量和重复兜底等信号决定保留、调整或删除条款。
