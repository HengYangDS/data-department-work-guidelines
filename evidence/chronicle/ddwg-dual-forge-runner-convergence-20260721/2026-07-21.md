# Chronicle: DDWG dual-Forge runner convergence — 2026-07-21

## Observation

At the start of this Change, GitHub reported no repository Actions runners and
no repository runner-label variable. Its documentation workflow selected
`ubuntu-latest` and installed Linux/browser dependencies. GitLab runner 48 was
project-scoped and online on macOS/ARM64, but its remote tag list was empty,
`run_untagged` was true, and `locked` was false; the GitLab job did not select a
tag. These observations made project/Forge isolation incomplete.

## Action

The repository now declares a GitHub selector comprising `self-hosted`,
`macOS`, `ARM64`, and a repository variable, with a same-repository pull-request
guard. It selects managed Node 22 and the local Chrome application instead of
provisioning a hosted Linux runtime. The GitLab job now selects the
`ddwg-documentation-ci` tag while retaining its separate Docker executor and
shared repository verifier.

## Evidence Boundary

This archived Chronicle records the initial control-plane observation and local
binding intent. The workflow-binding regression, GitLab static CI lint, and the
exact-HEAD local documentation proof passed before archive. It does not prove
that a GitHub runner is registered, a GitLab runner has been tightened, either
service is accepting jobs, either Forge received a published ref, any hosted job
has passed, or documentation has rendered on a provider.

## Revisit

After local closeout, retain provider-specific readback and run receipts: the
GitHub runner ID/labels, repository variable, workflow run ID, revision, and
conclusion; and the GitLab runner ID/tag/policy, pipeline and job IDs, revision,
and conclusion. A failure on either plane stays a failure on that plane; it must
not be masked by the other Forge's local runner or by local proof.
